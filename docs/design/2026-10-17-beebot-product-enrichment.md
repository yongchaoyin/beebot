# BeeBot 产品增强方案：让长期 AI 同事真正融入日常工作

状态：待产品审查的方案，不表示功能已实现。日期：2026-10-17。

依据：[竞品研究与代码基线](../research/2026-10-17-grok-muse-dots.md)。开发拆分、兼容策略和验收见[实施计划](2026-10-17-beebot-product-enrichment-plan.md)。本文件的交互、数据增量和优先级均为 BeeBot 设计建议。

## 1. 产品目标

BeeBot 应让用户拥有一组长期认识自己、职责明确、可以真实协作的 AI 同事。用户平时直接聊天；交代具体事情后，同事在授权范围内持续推进，必要时请用户判断，完成后交付可以继续使用的成果。

近期衡量标准是用户能否把一件日常事务完整交给 BeeBot，而非新增了多少模型、Agent、侧栏入口或状态机。先做好单 Bot 的独立价值，再让 Group 明显减少重复劳动。

保留现有产品约定：不强制每条消息成为任务，不设置必经的永久总管；群内是实际成员各自沟通与交接。个性、记忆、职责、能力、权限分别管理。原聊天是默认交流入口，管理弹窗只用于用户发起的创建或设置。

## 2. 首次使用：先成功交办一件事

新用户首先选择“这位同事主要帮你做什么”，可以从少量工作配方开始，例如资料研究、项目研发、日常事务。它们是填写职责和必要工具的起点，不自动生成一个万能团队。

创建过程沿用现有居中流程：名字与主要职责优先；头像沿用 Presence；模型和部署地点按实际环境选择。连接已有独立 Node 时，不先要求安装本机 Docker 或配置一个无关的本机模型。

用户进入聊天后，示例应与真实可用能力对应。例如没有接通邮箱时展示“整理你上传的报价”，接通并验证邮箱后才展示“根据今天收到的报价更新比较表”。连接过程中保留最初目标和草稿；完成认证后恢复那件工作，不要求用户重新解释。

每项能力区分“已配置”“尚未验证”“可用于当前任务”“需要你操作”。验证应使用经用户授权的、最小范围的真实检查，不能靠一个模型列表或接口返回 200 就宣布所有工具可用。

工作配方包含职责、典型输入、输出范例、所需工具、必要权限和试运行场景。发布前由用户选择共享内容；不携带账号密钥、私人聊天和未经确认的共享记忆。对一个 Bot 的能力描述不能替代试运行证据。

## 3. 连续聊天与工作上下文

### 3.1 对话不被工作打断

同一 Bot 可以一边做事，一边回答用户的新问题。长任务进行中，用户连续发第二、第三条消息，均应有明确归属和反馈，不吞消息、不清空尚未确认送达的输入。

例子：用户先要求整理项目需求，再说“第三部分先别写”，随后问“你现在依据哪份文档”。第一条补充影响相应工作范围；第二条问题得到直接回答。不能因为两条新消息到来就重跑整项工作，也不能把普通提问误当取消。

复杂事项允许展开一个工作详情或旁支交流，但主聊天保留关联。默认沿用当前会话和明确引用的工作；出现多个合理目标时，只问一次短问题，例如“这处修改指报价表还是项目周报？”。

### 3.2 选中后讨论

用户选中文本、文件段落、表格范围或已发布成果的一部分，可以“带到聊天”。输入框内形成可移除的来源引用，展示对象、选区和版本；不静默收集整个窗口或所有文件。

Bot 回答“把这段改得更简洁”时，能够回到具体对象及版本。目标已被改动时提示冲突并保留草稿；用户重新选择后才写入新版本。引用消息仍沿用紧凑的微信式样式。

第一阶段只做现有消息、附件与成果的明确选区。其他应用的选区、浏览器页面内容、代码范围在相应工具可以可靠提供身份和版本后再接入。

## 4. 用户看得懂的持续工作

### 4.1 三种信息，放在原有会话详情里

| 用户问题 | 建议展示 | 状态来源 |
| --- | --- | --- |
| 你正在忙什么？ | 当前事项、负责 Bot、下一步或实际阻碍 | 现有执行与协作记录的只读投影 |
| 有什么需要我处理？ | 一个具体问题、授权或登录动作，说明影响哪件事 | 当前有效的决策/审批记录 |
| 你长期在盯什么？ | 关注对象、通知条件、最近检查、下一次检查、交付位置 | 现有例行任务及其新增关注配置 |

这些是视图分类，不建立第三套任务账本。现有 collaboration panel 继续只读；修改、暂停、确认发生在相应会话动作或例行任务编辑入口，并经过原本的权限与版本检查。

聊天标题或头像旁只显示一条有意义的状态，如“正在比较三份报价”。详细工具输出收在展开区。没有新进展时不用不断发“仍在处理中”；错误、用户询问和真正阻碍则必须及时可见。

### 4.2 关注计划要能说清楚

当用户说“这个 PR 继续帮我盯着，有新的失败再告诉我”，保存的应是一项具体关注：哪个 PR、检查什么、什么时候算变化、怎样通知、什么时候停止。Bot 在聊天中确认这些已解析的边界，不要求用户填写整张任务表。

已有授权足以执行时直接建立；只读观察和自动修改代码是不同授权。用户说“盯着”不能默认为自动提交、合并或发布。用户明确要求修复并已授权相应操作时，后续仍可在该范围内推进，不反复要求相同批准。

通知示例：“这次 CI 新增一个失败，出在刚更新的依赖。我已经整理了原因，需要你决定是否升级依赖。”通知应带来源、相较上次的变化，以及下一步；一次故障不重复刷屏。

计划可暂停、改通知条件和结束。断网期间显示最后成功检查时间；恢复后是否补查必须由该类观察任务的策略明确决定，不把所有错过时段重新执行。当前已有无追赶调度规则保持兼容。

### 4.3 分开观察与执行

低打扰主动关注首先使用受限观察能力，只读取已授权资源并保存自己的记录。需要产生外部变更时，形成建议或进入既有的任务执行与审批链。

该边界需要工具、执行器和网络层实际约束，不能只在提示词中写“请只读”。没有受限执行能力的 Node 不显示“受限观察已启用”；可保留原例行任务，但必须准确描述它的能力边界。

## 5. 和 Bot 真正通话

本项目已有录音转文字入口。新的产品目标是应用内实时双向交流：用户说话、Bot 回答，用户能插话修正，必要时同一 Bot 继续操作原来的任务。

第一版从单 Bot 开始。会话标题旁增加电话入口；进入后保留当前聊天、显示正在听/正在说/正在做/等待决定的状态。沿用当前 Bot 的头像和身份，不新建“语音 Bot”。已有 Presence 承担状态变化，不先投入生成式视频形象。

关键交互示例：用户说“把刚才报价里的服务费单独列出来”。Bot 识别当前成果引用，回答并修改允许修改的版本。用户插话“先停一下，我说的是年度费用”，应停止当前语音输出并校正指令；不能把音频打断当成取消所有后台任务。

“挂断”结束音频连接，已明确交办的工作继续并回到聊天交付；“停止这件工作”走现有停止与不确定结果处理。界面必须区分两者，不能隐藏自动继续的行为。

接通前检验麦克风、音频提供方、语言和 Node 能力。文字模型配置不自动代表支持实时语音；可分别配置转写、对话、语音合成，或使用支持实时音频的提供方。失败时保留当前工作和文字输入，说明是哪一部分不可用。

第一版不承诺拨打真实电话号码、主动外呼或多 Bot 抢话式群语音。后续群语音也必须有实际发言者身份和调度；不能让一个声音假扮其他同事。实际电话网络接入应单独评估服务商、地域、成本与用户授权。

## 6. 可查看、纠正和共享的记忆

复用现有私有、用户共享、项目共享存储。会话详情提供“记忆与背景”，按作用范围查看；先补最常用的浏览、搜索、纠正、停止使用和显式共享，再考虑更复杂的自动归纳。

每条可管理记忆至少解释：内容、适用范围、来源、形成时间、是否由用户确认。不能从历史 Markdown 自动补出不存在的聊天来源；旧数据标为来源未记录。可选有效期和“有待确认”状态处理暂时信息与相互矛盾的内容。

例如用户说“以后报告先给结论”。可以保存为该 Bot 的偏好；用户进一步说“整个项目都按这个来”，才将它纳入明确的项目共享范围。Group 不因为同事之间认识就自动读出私聊信息。

纠正“预算改为八千”时，应更新作用于未来工作的记忆，并列出仍待处理的相关计划供核对；不悄悄改写过去的结果或已执行的订单。用户删除记忆后要说明删除的是未来召回条目，原聊天和已复制成果有各自的保留规则。

用户可以询问“为什么按这个偏好处理”，Bot 给出实际使用的可展示来源。不能把自我解释当作完整可验证的内部思考记录。模型推测必须与用户确认事实区别展示。

## 7. 成果继续协作，以及示范一次后复用

### 7.1 成果有稳定身份

在现有 Library 上增加“可以继续改”的体验。报告、表格、页面、代码交付有对象身份、来源消息、当前可用版本和责任 Bot。用户可以重新打开、引用其中一部分、要求修改，并回到产生它的那次工作。

“把昨天报告第二部分换成最新数据”应形成可比较的新版本。已发送给外部的旧版本保留回执；当前文件变化不能把旧回执变成发送了新版本。预览也不能被当作正式交付。

第一版优先可靠的文件/文档预览与编辑；交互卡片仅接受明确支持的类型或可信应用协议，能力受限。不能为了追赶“应用内应用”而直接执行聊天附件中的任意 HTML。

### 7.2 示范学习形成工作配方

沿用 Teach recording 和 learn-from-demonstration 入口，把录制之后的用户体验补完整：整理步骤、提取可变输入、列出工具与前提、用户纠正、隔离试运行，最后保存成版本化技能。

示例是“从后台导出这张报表，去掉作废项，按模板形成周报”。可变字段包括日期范围、筛选条件、输出位置；登录或管理员批准仍由用户或已有凭据机制完成。界面变化时允许重新理解任务，不按旧坐标盲目重放。

只有实际试运行的结果才能标为“已验证用于该场景”；仅录制成功标为“待验证”。多 Bot 共用时发布技能定义和依赖，不复制示范期间看到的账号与私密业务数据。

## 8. 连接真实工作工具，并在离开电脑后接着用

先把少量高频工作闭环做完整。研发场景优先 GitHub，办公交付优先选择一个邮箱提供方与一种文档/表格入口；连接器数量不是验收目标。依次验证读取、生成草稿、选择真实账号、确认、执行、核对回执与后续查询。

现有 Slack MCP 发送、自动化监听与一个完整外部聊天 Bot 是不同能力。后续首个外部渠道必须同时解决收到消息、身份关联、引用原事项、返回结果和处理一次必要决定，不能只展示一个可发送的按钮。

手机入口先做当前事项、消息和明确确认即可，不需要立即复制完整桌面管理功能。远端服务器继续持有账号及工作状态；手机与 Mac 面向同一 Bot。来自不同设备的过期确认不能覆盖最新内容。

“拿到一个 Bot 邮箱地址”不是近期前置条件。优先让用户自己的现有账号可靠工作；独立邮箱涉及入站身份、垃圾邮件、引用归属等另一组产品问题，后续再单独交付。

## 9. Group 的差异化价值

Group 应让用户看见必要的讨论与实际分工，并能直接找任意成员。每个 Bot 的主要职责保持可见，但责任认领依赖当前任务与实际能力，不凭名字“测试专家”就认定它会测试。

一次群任务可以由不同同事临时推进。示例：研究同事比较方案，开发同事实现，测试同事复核证据；需要独立思考时明确邀请讨论。无须所有人对每条消息发表意见，也不让一个协调者冒充三个人。

共享记忆、技能与成果应指向相同项目上下文，同时保留每个 Bot 私有记忆边界。群任务的成果既能从 Group 找到，也能沿消息追到实际作者。个人 Bot 离开某个 Group 后仍是可独立使用的同事。

远程成员能力尚未对等时，界面准确显示当前限制。先实现身份、上下文引用与状态展示一致，再交付实际跨节点委派和成果传输；不把远端描述字段冒充本地已确认职责记录。

## 10. 首批验收场景

| 场景 | 用户得到的完整结果 | 必须包含的转折 |
| --- | --- | --- |
| 项目研发跟进 | 一个明确的 PR/问题被持续关注，有新问题才通知，修复经过当前授权和真实检查 | 途中连续补充两条要求，CI 重复事件，权限失效，进程重启 |
| 报价整理与邮件回复 | 资料形成比较表，用户改一处后，从所选账号发出准确版本 | 账号切换、内容变更、重复点击、未知发送结果 |
| 语音交办日常事项 | 通话可以围绕已有工作继续，挂断后结果回到原会话 | 插话、更正、麦克风失败、网络断开、显式停止工作 |
| 教会一项每周工作 | 录制形成可读配方，经试跑后按明确计划执行 | 输入日期变化、页面变化、依赖不可用、用户暂停 |

## 11. 实施顺序与暂缓事项

第一批应完成“交办—持续关注—需要决定—交付—再修改”的一条高频路径，同时清理该路径上的上游依赖与假就绪状态。语音与记忆管理作为明确的小阶段接入，不等待整个分布式系统重写。

随后完成一个外部渠道或手机入口，让同一件工作离开 Mac 仍可继续；再推进跨 Node Group、更多成果类型和技能共享。自主渲染器按独立迁移计划演进，每个产品阶段仍须验证实际打包入口。

本方案暂不安排开放市场、公共多租户、自动跨节点容灾、生成式视频头像、硬件、全渠道齐发或无限制自主支付。这些不是现有用户完成日常协作的必要前提。

## 12. 成功指标

建立基线后再定目标数值，当前不虚构成功率。持续观察：首次得到可用成果的时间；一次任务需要用户重复解释和催促的次数；交付后能直接使用的比例；无价值通知比例；来源引用和记忆纠正的有效率；每项任务的实际费用与执行次数。

重复外部动作、错误账号发送、已删除记忆再次未经允许共享，作为单独的质量事件统计。群任务要证明实际分工减少重复劳动；单 Bot 也必须通过同样的连续消息与交付检查。
