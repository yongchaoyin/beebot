基线：`origin/main` 的 `ce1d8e0652d1f5bb00d2739d7a79388bb3a74ceb`。
阅读顺序：[研究与来源](../research/2026-10-17-grok-muse-dots.md) → [产品方案](2026-10-17-beebot-product-enrichment.md) → 本文。

## 1. 采用渐进式产品交付

先完成一个高频事务的端到端使用，再扩大能力与部署范围。共同产品概念不意味着立即替换全部持久化：本地 collaboration、Node v1 Goal/Task/Run、automations、draft delivery 继续各自持有现有权威状态，通过显式适配提供统一展示。

每个阶段必须说明当前覆盖本地 Bot、本地 Group、独立 Node 的哪些组合。功能不支持时返回明确能力缺失，不借用本地身份、模型、账号或旧缓存伪装成功。远程旧协议的用户确认机制不在读取时自动转换成本地 Bot 自检完成。

本阶段文档不批准任何自动发布、发邮件、支付或合并行为。后续实现必须沿用用户已有授权与原有副作用保护；调用新增工具或接入一个账号不自动扩大 Bot 的工作职责。

## 2. 阶段及完成门槛

| 阶段 | 完成后的用户能力 | 实现范围 | 进入后续阶段的门槛 |
| --- | --- | --- | --- |
| S0 能力与依赖核实 | 看懂该 Bot 当前能做什么，缺什么可以原地处理 | 选定首条真实业务路径；核对提供方、账号、模型、执行位置与正式 UI；补有限能力描述与可恢复设置入口 | 没有配置即成功、占位功能可点击、失联即任务失败等误导；保留目标和草稿 |
| S1 连续工作闭环 | 交代一件事、继续聊天、看到进展与必要决定、拿到结果 | 原会话详情投影，目标引用与有效决策，复用协作和 Library，先覆盖本地 Bot/Group | 第二第三条消息可处理，状态来自真实记录，所有结果可回到来源；不强迫普通聊天建任务 |
| S2 持续关注与真实交付 | 关注具体对象，有变化才通知，确认后通过实际工具交付 | 例行任务关注配置、受限观察、交付目的地；优先一个实际邮箱或研发工具闭环 | 重复事件不重复通知或动作；真实连接器验证账号、版本与回执；失败可恢复 |
| S3 实时通话 | 在原 Bot 会话里说话、插话、交办，挂断后工作继续 | 音频会话、提供方适配、与现有消息/执行分离的取消生命周期 | 实际麦克风和音频提供方测试，文字与语音状态一致，不跨 Bot 误投，不把挂断当停止任务 |
| S4 记忆与可复用成果 | 纠正记忆，引用和修改成果，把示范变成可用技能 | 现有记忆存储的管理 API/UI、范围与版本；Library 增量；Teach 的验证和发布步骤 | 旧资料不编造来源，共享可撤销；成果并发修改有冲突保护；技能完成真实试跑 |
| S5 跨入口连续使用 | 从手机或一个外部消息渠道接手同一件事 | 优先一个入口；服务端 Bot 身份、会话、决策和结果关联；独立 Node 能力协商 | 换设备后看到同一权威状态，旧审批不能确认新动作，重复来信/回调不重复执行 |
| S6 跨 Node Group | 本地和远端同事真实分工、传递成果、恢复连接 | 协议演进、成员/角色版本、成果访问、任务归属和中断核验 | 双认领、旧结果晚到、断网和取消场景均有明确结果，无隐式副作用重放 |

S3、S4 可以在 S0 的能力边界确定后独立进行，不要求等待 S6。每个阶段单独审查、提交、验证；未通过的阶段不能靠累计后续功能掩盖问题。自主渲染器迁移另立计划，不和首个产品闭环绑成一次大改。

## 3. S0：先查实际提供方

重点代码如下，列出的都是现存入口。

| 领域 | 先读的实现 | 需要回答的问题 |
| --- | --- | --- |
| 模型与 Host | [Host composition](../../source/host/host-runner-composition.ts)、[模型提供方配置](../../source/shared/inference-vendor.ts) | 该模型是否支持当前工具、图像、流式、上下文需求？哪些已测，哪些只是声明？ |
| 语音 | [录音入口](../../frontend/src/recovered/features/conversation/workspace/voice.tsx)、[上游转写](../../source/electron-main/account/cursor-transcribe.ts)、[账号接线](../../source/electron-main/account/cursor-auth-wiring.ts) | 本地自选模型配置是否仍会调用上游转写？没有上游账号时怎样准确呈现？ |
| 审批 | [Auto-review](../../source/host/extensions/auto-review/extension.ts)、[分类器](../../source/host/extensions/auto-review/sand-backend-smart-mode-classifier-exec.ts) | 哪些授权由本机规则决定，哪些依赖上游服务？不能用模型自我判断替代哪个边界？ |
| 外部动作 | [草稿服务](../../source/host/extensions/transcript/draft-delivery.ts)、[监听服务](../../source/host/extensions/automations/listener-integrations.ts)、[渠道声明](../../source/shared/channels.ts) | 读取、监听、草稿、确认、发送、收件是否真正分别可用？ |
| 远端 | [连接管理](../../source/client-connections/manager.ts)、[Node 控制库](../../source/node/control-store.ts) | 服务端声明什么能力，当前主体具有什么权限，是否真的具备执行条件？ |
| 正式 UI | [renderer adapter 入口](../../scripts/lib/router-renderer-patch.mjs)、[ProductionRenderer](../../frontend/src/production/ProductionRenderer.tsx) | 修改是否进入真实打包的 renderer？是否依赖不在正式路径上的可读镜像？ |

建议的能力描述至少区分提供方支持、用户授权、执行环境可用和最近验证结果。验证结果绑定 Node、连接主体及配置代次，不跨账号复用。原始字段只用于协议和诊断，普通 UI 给出具体可执行的下一步。

S0 不自动扫描全部私人应用或调用有副作用的“测试发送”。读取检查只针对用户选择的工作与授权对象；需要真实发送验收时使用明确授权的测试对象。

## 4. S1：统一展示，保持权威状态不变

复用 [collaboration context](../../source/host/extensions/transcript/collaboration-context.ts)、[controls](../../source/host/extensions/transcript/collaboration-controls.ts)、[completion](../../source/host/extensions/transcript/collaboration-completion.ts) 和 [Group orchestrator](../../source/host/extensions/transcript/group-chat-orchestrator.ts)。

建议只读工作投影包含：来源类型、来源 ID、Node/会话/责任 Bot、标题、当前状态、状态版本、阻碍、有效决策引用、成果引用。展示状态不是新的可执行状态机，写动作仍发给原来源。

用户补充指令带明确的会话或目标引用；兼容旧自然语言消息。引用需要验证当前成员、实际来源与可访问范围。未知或歧义目标不能静默选择另一个项目。修改范围不自动重跑原有有副作用步骤。

决策卡必须绑定当时的对象版本和用户看到的内容。已经失效的审批在历史中保留，但不能继续接受；成功回复不冒充已执行成功。普通工作完成仍按已有 owner/peer 检查，只有确实需要用户判断或新增授权时才出现用户动作。

## 5. S2：关注配置与交付绑定

复用 [Automation store](../../source/host/automations/automation-store.ts) 与 [Local scheduler](../../source/host/extensions/automations/local-routine-scheduler.ts)，在现有 routine 上增加版本化关注配置，避免另造一套计划调度器。

建议新增配置语义：被关注资源、观察条件、通知条件、交付会话/收件范围、结束条件、时区和静默时段。最近观察与已通知状态分开保存；发现变化不等于已经通知成功。没有真实事件能力时，清楚使用定时检查，不声称实时监听。

观察任务应通过明确的只读工具与受约束执行器运行。允许任意 Shell/浏览器写入的通道不能标为只读；未知工具能力拒绝进入观察通道。需要写入时转入实际授权的工作或产生待决事项。

结果通知沿用成功 SendMessage 的公开边界。稳定事件标识与通知摘要用于去重，但不能吞掉后来发生的另一项真实变化。目标范围、计划和账号变更必须使过期候选失效。

真实外部交付扩展 [draft delivery](../../source/host/extensions/transcript/draft-delivery.ts) 的已验证适配器。按照提供方的实际 schema 映射参数与回执，不通过名称猜测发送工具。仍在 `sending` 或 `needs-review` 的记录，不能通过切换账号或刷新页面重新发送。

## 6. S3：语音与工作生命周期分离

建议增加明确的 CallSession，包含会话、Bot、Node、音频提供方、语言、连接代次和状态。它不承载任务完成状态；音频转写后的用户指令进入既有消息通道。

两种实现路线先做能力评估：实时音频模型；流式转写加现有文本推理和语音合成。前者可能减少中间环节，后者更容易复用多模型配置；两者都需要真实测量插话、工具调用期间反馈和首段音频时间，不能仅凭接口类型选型。

音频链路停止、Bot 当前发言停止、某项工作停止分别建模。明确的用户取消按现有任务控制传播；模型音频截断不推导外部操作已取消。断线重连绑定原 CallSession 代次，晚到音频不能在新会话播放。

先确认说话人与用户权限。收音内容中的人名或第三方说话不能天然成为已认证的审批人；涉及具体敏感动作时沿用实际可验证的确认入口。通话文字记录、音频保存与保留期提供清楚的用户选项。

## 7. S4：在现有存储上补管理能力

### 记忆

复用 [memory-service](../../source/host/extensions/memory/memory-service.ts) 和 [project-membership](../../source/host/extensions/memory/project-membership.ts)。不把已有文件格式直接强制改写成全新库。

新元数据可逐步补充作用范围、来源引用、来源是否已核实、有效期和修订号；历史事实没有证据时保持未知。更新与共享需要当前范围、主体和版本校验。用户明确删除与自动合成的淘汰分别处理，不让下一次合成悄悄重新共享用户刚删除的条目。

读取与管理本身不能扩大 project membership 或 primary job。撤销共享后，后续召回停止使用；已执行成果与其他持久副本的处理需显式追踪，不能承诺“从所有历史彻底消失”。

### 成果

复用 [Library adapter](../../scripts/lib/beebot-conversation-library.snippet.js)、原附件读取桥和协作 evidence。先定义对象身份与版本引用，再增加局部编辑。外部平台文档与本地文件可以使用不同适配器，但都需返回确切对象和版本状态。

原消息、成果当前版本、发送时版本、外部回执分开。网络失败和版本冲突保留用户修改，不把未知写入自动重放。跨 Node 文件仍走授权传输，不把远端路径当成本机路径读取。

### 技能

复用 [Teach service](../../source/host/extensions/teach-recording/teach-recording-service.ts)。技能依次经历草案、待试跑、已验证于指定场景和已停用；这是能力记录，不是执行权限。

第一轮用隔离测试账号和非生产数据演示完整“录制—生成配方—用户纠正—试跑—按计划复用”。受限环境无法运行的步骤保留缺口，不能用录制测试替代真实学习结果。

## 8. S5/S6：跨入口与跨 Node 分开验收

先解决同一个独立 Node 的多入口连续性，再增加多个 Node 之间的真实分工。前者依赖会话归属、可靠事件、确认与送达；后者额外需要跨节点授权、任务责任与成果访问。

协议能力缺失采用显式协商。不把远端 description 解释为已确认 primary job，不给旧 Node 发送不认识的字段再悄悄丢弃重试。

现有 Node Goal/Task/Run 和本地 collaboration 先建立可审查的映射，特别是 completion、review、cancel、uncertain 的差异。每个权威对象只由一个归属方负责写入；不可用的源数据显示最后确认状态和时间。

迁移需要版本化存储备份、只读预览、确定性的对象映射与失败恢复说明。不得在一次读快照中迁移任务、扩大成员权限或触发外部调用。以[分布式设计决策](../distributed-hive-decisions.md)为已有参考，避免另起一套同义协议。

## 9. 必须覆盖的验收矩阵

| 类别 | 场景 | 预期结果 |
| --- | --- | --- |
| 连续聊天 | 单 Bot 与 Group 忙时连续发第二、第三条消息 | 不吞消息、不清错草稿；补充、提问和取消各自处理 |
| 群协作 | 多 Bot 可参与，但一个任务范围已有人认领 | 保留真实讨论，避免未经需要的重复工作；不冒充同伴 |
| 导航 | 切换 Bot、关闭详情、退出设置期间返回晚到请求 | 不改变新会话、旧草稿或错误账号的 UI |
| 记忆 | 退出项目、纠正偏好、删除后自动合成 | 后续范围与内容正确，不让旧共享状态复活 |
| 主动跟进 | 无变化、重复事件、暂停后晚到事件 | 沉默或明确忽略；暂停不等于新授权；不重复外部写入 |
| 时间 | 时区变化、夏令时、设备休眠、Node 离线 | 显示实际最近/下次检查；遵守已声明补查规则 |
| 真实交付 | 换账号、修改内容、双击、超时、回执缺失 | 正确指向所审内容与账号，未知效果待核验 |
| 语音 | 插话、挂断、明确停止工作、音频晚到 | 语音和任务取消边界清楚，结果回原会话 |
| 文件 | 并发修改、附件不可读、远端文件未传到 | 保留草稿和旧版本，不提前展示“可用成果” |
| 示范学习 | 页面变化、依赖缺失、录制结束但学习失败 | 提供可修复配方，不宣称学会，不盲重放步骤 |
| 部署 | 没有上游账号、只有自选模型、远端协议较旧 | 明确能力范围，不伪造本地初始化和模型就绪 |
| 界面 | 中文/英文、明暗主题、窄窗、键盘、输入法 | 真实 packaged renderer 路径可用，状态变更不偷焦点 |

## 10. 验证层级与交付记录

按修改内容运行必要检查。类型与单元/组件测试证明局部契约；真实 Node/Host 集成证明执行和持久化；macOS 原生及 packaged renderer 证明用户实际安装路径；真实模型与已授权连接器测试证明所选业务场景。

四种证据不能互相替代。每次记录代码 SHA、模型/提供方、场景、是否使用 fixture、实际结果、跳过内容与原因。既有 `npm run smoke` 的 clean-renderer 前提问题单独报告，不削弱校验使其转绿。

新增测试应保护可观察的产品行为和失败恢复，不写只镜像实现的断言。通过所需检查后继续提交，不为凑数量反复运行不相关测试。

当前研究交付只包含 Markdown。验收范围是来源登记、代码链接存在、文档间一致性与 Git diff；没有把历史集成记录当作本轮测试，没有更改产品代码、安装应用或运行真实外部发送。

后续每阶段提交代码、必要回归与 `docs/` 说明到独立分支，核对远端 SHA 后再报告推送成功。默认分支合并另行遵守用户授权。
