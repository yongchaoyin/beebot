# 自然同事交流与执行交付边界

基线：`db2745d87d0838df806b716d406cb18f63cec4db`（PR #18）。
本轮不改主题、头像、引用结构、模型绑定、Node 认证或持久消息协议。

## 用户现象与已复现的原因

普通能力讨论中，Bot 已用 SendMessage 回复，随后又向群聊发送
“已回复用户（消息已发出）／本轮处理”等内部收尾总结。

真实 HTTP 推理适配器原先把每次 **stream** 中没有 tool-call 的非空文本自动包装成
一个 `synthetic-send-*` 的 SendMessage。一次用户回合可能包含多次推理；它没有区分
第一次回答、工具结果后的继续推理、内部压缩或最终收尾。于是：

1. 第一轮推理真实调用 SendMessage，用户已经收到答案。
2. 下一轮模型输出私有收尾文本，没有工具调用。
3. 适配器伪造第二个 SendMessage，群聊发布层把它当成真实回复。

不仅是重复总结的问题：没有先发公开回复时，任何非空私有文本也可能被错误公开。
只检测“此前是否发过消息”仍不能修复这个边界；按“总结”等关键词隐藏界面同样不正确。

## 硬性修复：公开消息不能由私有文本推断

`httpVendorExecutor` 原样转发 SDK 的 `fullStream`，删除 synthetic fallback：

- Host 的工具会话中，只有真实 SendMessage 能进入公开消息链路。
- 普通 text-delta 仍交给 runner、检查点与内部状态；不丢弃模型文本，不清空内部记忆。
- 已有纯文本直接返回路径 `runRoutedProviderText` 仍消费 text-delta 并返回答案。
- 不把真实 SendMessage 改名、删内容或合并；用户明确要求的总结、合法任务结果照常发送。
- 子 Agent 的最终文本仍返回父 Agent，不直接对用户发消息。
- 模型不按工具协议回答时，保留既有的回复提醒／失败处置；不以伪造工具调用冒充发送成功。

这项修复不依赖消息语言、关键词或 UI 是否折叠。普通 SendMessage、真实工具错误、任务账本、
停止／冻结／待核查和引用原消息机制不改。

## 同事行为：先理解当前交流，再决定是否执行

增加共享 `COLLEAGUE_CONVERSATION_POLICY`，接入主 Agent、群成员和 provider 备用系统提示；
外部频道的节奏说明与其对齐。它是交流约束，**不是新的自动任务分类器或权限授予器**。

| 场景 | 期望行为 | 不应发生 |
| --- | --- | --- |
| 问候、普通问答 | 直接说必要的一句话／答案，然后结束 | “收到—本轮处理—已回复”的三段流程 |
| 能力讨论、方案商量 | 结合已知上下文表态，给出可行下一步，只问影响下一步的关键缺口 | 通用能力菜单、重复索取已知背景、讨论即擅自发布 |
| 清楚且已授权的任务 | 明确实际第一步，执行并产出；需要同事时真实交接 | 只列“你可以怎么做”，把所有操作交还给用户 |
| 执行中的追问 | 从当前记录回答状态，解释新增约束是否已生效 | 重置需求、无依据报进展、把“收到了”当成“改好了” |
| 已执行的工作 | 一次交付结果／位置／验证／真实阻塞；复杂工作只报有意义的节点 | 先交付，再复述“我已经交付了什么”的第二篇总结 |
| 明确要求总结材料或讨论 | 总结本身就是用户要的答案 | 因包含“总结”字样被隐藏或拒绝 |
| 内部记账、回合收尾 | 留在内部状态 | 发到普通聊天当成果或执行报告 |

是否执行依赖上下文中的实际意图，而非单一关键词。“可以帮我写三条标题吗”可能就是任务；
“能运营账号吗”也可能还在确定方向。用户无需切换“问答／员工模式”，无需每次加口令。
真正要求的计划、文稿、分析本身也可以是交付，不能机械地以“调用过工具”作为唯一执行证据。
方案与承诺则不能证明其中计划的外部动作已经发生。

## 以截图场景说明

用户问“可以帮我运营小红书或者抖音吗”，没有更多已知背景时可以自然回答：

> 可以，先把账号定位和内容做好。你主要想做个人品牌还是产品推广？

这是一句讨论回复，不启动发布任务，也不追加“本轮处理：已解释能力”。
如果上下文已经明确账号方向，不应再次询问同一个问题。

用户随后说“产品推广，先写一周选题，不要发布”，应实际形成选题草稿而非再次解释能做什么。
完成后交付草稿并说清未发布；需要协作就通过已有真实 Bot 消息交接，不替其他成员说话。
以上仅为产品行为示例，不是假装已经操作了用户账号。

## 不被改变的安全与协作条件

主动性不增加权限。外部发布、发信、支付、登录、跨用户数据访问等仍受既有授权和审核约束。
群成员之间的请求不扩大用户授权；既有 claim/version/review、成果核验、交接与未完成责任继续保留。
不会按内容相似度删除消息，不改写历史，不回放旧失败任务。常规问答不会因本轮补丁创建正式任务。

## 回归与可重跑命令

使用仓库锁定 Node 26.5.0 与依赖。测试模型是仅监听 loopback 的受控 SSE 服务，不使用真实 API Key。

```sh
node --test tests/provider-delivery-boundary.test.mjs tests/http-tool-parameters.test.mjs tests/publication-packaging.test.mjs
npm run node:build
BEEBOT_RUNTIME_INTEGRATION=1 node --test tests/node-runtime.test.mjs
npm run source:typecheck
npm run typecheck
```

新增测试不替换生产 HTTP 适配器或 SendMessage 边界：

- 真实 AI SDK／HTTP 适配：先发送回答，再返回分段内部总结；只有一个真实公开调用。
- 即使没有先前 SendMessage，私有文本也不自动公开。
- 明确 SendMessage 的总结不被文字过滤，原 toolCallId 保持。
- 纯文本路径完整返回答案和流式 delta。
- 真实群发送队列／SQLite：上一条仍运行时继续发送第二、第三条，答案与 replyTo 一一对应，
  不产生额外总结或正式任务。进入运行前合并的消息突发仍可按既有策略合并，不强制一消息一任务。
- 主 Agent／群／provider 使用同一政策，子 Agent 的内部最终报告仍保留。
- 真正启动独立 Host、执行器与 Shell，跨同一个 Bot 的四个持久回合验证：普通澄清 →
  真实写文件并交付 → 谢谢 → 明确要求总结。公开消息分别为 1／2／1／1 条；
  任务中的开始说明与实际结果都保留，四次内部收尾都不公开，文件内容保持。

曾在基线只还原旧 provider/helper 后运行新边界测试，三个相关场景确实失败：私有总结被伪造为
SendMessage、没有工具时的文本被公开、群记录变成两条。修复后同一路径通过。
旧的“无工具文本应该自动 SendMessage”测试与新产品边界相冲突，已替换为真实 provider／群／Host
行为回归，不是删除失败用例以取得绿色结果。

## 验收范围与限制

受控模型响应证明消息路由与持久化边界，不能证明任意供应商模型已经具备员工水平的规划、判断
与长期记忆。提示词统一能减少能力菜单和无意义收尾，但若模型**显式**调用 SendMessage 重复回答，
本轮不会按猜测吞掉它；这仍需真实模型会话评测。也没有新增无人值守发布权限。

未读取用户电脑、Keychain、账号或真实社交平台；没有付费模型调用、真实跨机团队完整验收。
主干不自动合并，安装包不自动发布。历史已经公开的总结消息不会被本轮删除。
